# Звіт до лабораторної роботи №2

## Тема

Розробка клієнтського TypeScript-застосунку для управління бібліотекою.

## Мета роботи

Мета роботи - створити односторінковий застосунок, у якому можна додавати книги та користувачів, переглядати списки, шукати записи, позичати та повертати книги. У проєкті використано класи, інтерфейси, generics, ES-модулі, DOM API, Bootstrap, Webpack, Vite, LocalStorage та автоматичні тести.

## Структура проєкту

Основний код знаходиться у директорії `app-library`:

- `src/models` - класи предметної області `Book` і `User`, а також їхні інтерфейси.
- `src/services` - бізнес-логіка бібліотеки та робота зі сховищем.
- `src/utils` - функції валідації даних.
- `src/ui/components` - окремі DOM-компоненти форм, кнопок і модального вікна.
- `src/ui/render.ts` - рендеринг списків книг і користувачів, пагінація та дії зі списками.
- `src/app.ts` - точка запуску застосунку, форми та координація стану.
- `src/styles` - SCSS-стилі та імпорт Bootstrap.
- `tests` - тести класів `Library` і `Validation`.
- `webpack.config.js` і `webpack.index.html` - конфігурація та HTML-шаблон Webpack.
- `vite.config.ts` і `index.html` - конфігурація та HTML-точка входу Vite-варіанта.
- `dist` і `dist-vite` - результати production-збірок.

# Практична частина

## 1. Ініціалізація проєкту та встановлення залежностей

Проєкт створено як окремий npm-проєкт у директорії `app-library`. Його опис і всі залежності знаходяться у файлі `package.json`.

Для роботи застосунку встановлено такі основні залежності:

- `typescript` - статична типізація TypeScript-коду;
- `webpack`, `webpack-cli`, `webpack-dev-server` - збірка та локальний dev-сервер;
- `ts-loader` - передавання TypeScript-файлів у Webpack;
- `sass`, `sass-loader`, `css-loader`, `style-loader`, `mini-css-extract-plugin` - обробка стилів;
- `html-webpack-plugin` - генерація HTML-файлу під час збірки;
- `bootstrap` - UI-фреймворк;
- `mocha`, `chai`, `tsx` - запуск тестів TypeScript-коду;
- `eslint` і `prettier` - перевірка та форматування коду;
- `husky` - запуск перевірок перед комітом.

Основні npm-команди:

```bash
npm run start       # Webpack dev-сервер на порту 9000
npm run build       # production-збірка Webpack
npm run start:vite  # Vite dev-сервер
npm run build:vite  # production-збірка Vite
npm run typecheck   # перевірка TypeScript без створення файлів
npm run lint        # запуск ESLint
npm test            # запуск Mocha-тестів
```

Тестова команда саме для цього проєкту - `npm test`, а не `npx jest`, тому що в завданні передбачено Mocha.

## 2. Ознайомлення з архітектурою та дизайном

Проєкт розділено за відповідальністю, щоб бізнес-логіка не залежала від DOM.

Моделі знаходяться у `src/models`, сервіси - у `src/services`, допоміжні функції - у `src/utils`, а UI-компоненти - у `src/ui/components`.

Основна координація застосунку відбувається у `src/app.ts`. Цей файл створює бібліотеки книг і користувачів, налаштовує форми, збереження стану та передає дані до `src/ui/render.ts`. Окремий файл `ui/render.ts` відповідає за списки, пошук, пагінацію та кнопки дій.

Візуальний напрям відповідає наданому макету: застосунок містить заголовок, форму додавання книги, форму додавання користувача, списки книг і користувачів, кнопки позики/повернення, повідомлення та модальні вікна.

## 3. Налаштування Webpack

Конфігурація знаходиться у `webpack.config.js`.

Основні налаштування:

- `entry: './src/app.ts'` - точка входу застосунку;
- `output` - директорія та назва зібраного JavaScript-файлу;
- `resolve.extensions` - підтримка імпортів TypeScript-файлів;
- `ts-loader` - компіляція `.ts`;
- Sass-лоадери - обробка `.scss`;
- `MiniCssExtractPlugin` - винесення CSS у окремий файл у production-збірці;
- `HtmlWebpackPlugin` - підключення зібраних ресурсів до HTML;
- `devServer.port: 9000` - локальний сервер за адресою `http://localhost:9000`;
- `hot: true` - оновлення змінених модулів без повного перезавантаження сторінки.

Запуск:

```bash
cd app-library
npm start
```

## 4. Підключення Bootstrap

У проєкті використано Bootstrap 5.3.8 як npm-залежність.

Bootstrap імпортується у `src/styles/main.scss`:

```scss
@use 'bootstrap/scss/bootstrap';
```

SCSS-файл імпортується у `src/app.ts`, після чого Webpack обробляє його відповідними loaders. CDN у `index.html` не використовується. Це означає, що UI-фреймворк входить до локального dependency-графа та обробляється бандлером.

## 5. Орієнтація на макет із `app-design`

За основу взято макет системи управління бібліотекою. У застосунку реалізовано:

- заголовок системи;
- форму додавання книги з назвою, автором і роком;
- форму додавання користувача з іменем, email та ID;
- список книг;
- список користувачів;
- кнопки дій праворуч у рядках списків;
- модальні повідомлення про позичання та повернення;
- повідомлення про помилки;
- пошук і пагінацію.

Структура і поведінка реалізовані програмно, тому інтерфейс оновлюється після кожної операції без ручного редагування HTML.

## 6. Генерація UI програмно

HTML-шаблон Webpack знаходиться у `webpack.index.html` і містить тільки кореневий елемент:

```html
<div id="app"></div>
```

Для Vite використовується кореневий `index.html`, у якому додатково підключено `src/app.ts` через `<script type="module">`. Форми, списки та кнопки створюються у TypeScript. Основна розмітка форм і контейнерів створюється у `src/app.ts`, а списки, кнопки дій і пагінація - у `src/ui/render.ts`. Допоміжні компоненти знаходяться у `src/ui/components`.

Після додавання або видалення даних застосунок повторно формує потрібну частину DOM через `replaceChildren`, `append` та створення елементів. Обробники подій підключаються до кнопок і форм із TypeScript.

Такий підхід відповідає вимозі не розміщувати готову декларативну розмітку бібліотеки в `index.html`.

## 7. Класи та інтерфейси для книг

Контракт книги описано в `src/models/interfaces/IBook.ts`.

Клас `Book` знаходиться у `src/models/Book.ts`. Він зберігає:

- унікальний ID;
- назву книги;
- автора;
- рік видання;
- стан позики книги.

Методи класу дають доступ до властивостей та змінюють стан книги:

- `getId()`;
- `getTitle()`;
- `getAuthor()`;
- `getYear()`;
- `isBorrowed()`;
- `borrow()`;
- `returnBook()`;
- `toJSON()`;
- `toString()`.

Клас приховує деталі зберігання стану та надає контрольований API для роботи з книгою.

## 8. Класи та інтерфейси для користувачів

Контракт користувача описано у `src/models/interfaces/IUser.ts`.

Клас `User` знаходиться у `src/models/User.ts`. Він зберігає ID, ім'я, email і список ID позичених книг.

Основні методи класу:

- методи отримання ID, імені та email;
- `borrowBook()` - додавання книги до списку користувача;
- `returnBook()` - повернення книги;
- `getBorrowedBookIds()` - отримання списку позичених книг;
- `toJSON()` - підготовка даних до збереження.

Бізнес-правило про максимум три книги реалізоване всередині `User`, тому воно використовується однаково незалежно від UI.

## 9. Generic-клас `Library<T>`

Клас `Library<T>` реалізовано у `src/services/Library.ts`.

`T` означає тип об'єкта, яким керує бібліотека. Тому один і той самий клас можна використовувати і для книг, і для користувачів, не втрачаючи типізацію.

Клас приймає функцію `getId`, яка визначає, як отримати ID об'єкта. Основні методи:

- `add()` - додає об'єкт, якщо його ID ще не існує;
- `remove()` - видаляє об'єкт або ID;
- `findById()` - шукає об'єкт за ID;
- `find()` - шукає об'єкти за умовою;
- `getAll()` - повертає всі об'єкти;
- `clear()` - очищає колекцію;
- `size` - повертає кількість об'єктів.

У `src/app.ts` створюються дві колекції:

```ts
const books = new Library<Book>((book) => book.getId());
const users = new Library<User>((user) => user.getId());
```

Якщо додати об'єкт із повторним ID, `Library` його не додає.

## 10. Клас `Storage` і LocalStorage

Робота зі сховищем реалізована у `src/services/Storage.ts`.

Клас використовує браузерний `localStorage`. Дані перетворюються у JSON:

- `save<T>(value)` - серіалізує та зберігає значення за ключем, який задається у конструкторі;
- `load<T>(fallback)` - читає значення цього ключа та розбирає JSON;
- `remove()` - видаляє ключ сховища;
- `clear()` - очищає LocalStorage.

У `src/app.ts` створюється `new Storage('library-management-state')`. У цьому ключі зберігаються книги, користувачі та списки ID позичених книг користувачів.

Під час запуску функція відновлення читає цей ключ і створює об'єкти `Book` та `User` з отриманих даних. Після зміни стану функція `persist()` знову серіалізує дані та записує їх у LocalStorage.

Обмеження LocalStorage: дані доступні тільки у браузері цього користувача, зберігаються у форматі рядків, мають обмежений обсяг і не підходять для спільної серверної бази даних.

## 11. Модулі та простори імен

У проєкті використано ES-модулі: класи та функції експортуються через `export` та імпортуються через `import`.

Приклади розділення:

- `Book` імпортується з `models/Book`;
- `Library` імпортується з `services/Library`;
- `Storage` імпортується з `services/Storage`;
- `Validation` імпортується з `utils/validators`.

Функціональність `Validation` реалізована як експортований об'єкт із методами, а не як TypeScript `namespace`. Це сучасний модульний підхід для цього проєкту. ES-модулі відповідають за поділ файлів і залежностей, а namespace групує оголошення в одному просторі імен.

## 12. Позичання та повернення книг

Позичання складається з таких кроків:

1. Користувач натискає кнопку «Позичити» у списку книг.
2. Перед кнопкою користувач обирається зі списку `<select>`. Значенням option є ID користувача.
3. Обробник кнопки знаходить користувача через `users.findById(select.value)`.
4. Перевіряється, чи користувача обрано та чи не досягнуто ліміту у три книги.
5. Відкривається модальне вікно підтвердження через `showModal()` із `src/ui/components/Modal.ts`.
6. Після підтвердження `Book.borrow()` змінює стан книги на позичений.
7. `User.borrowBook()` додає ID книги до списку користувача.
8. `persist()` зберігає новий стан через `Storage` у LocalStorage.
9. `notify()` показує повідомлення, а функція `render()` у `app.ts` повторно викликає `renderLibrary()` з `ui/render.ts`.

Повернення працює у зворотному напрямку:

1. Користувач натискає «Повернути».
2. Для книги знаходиться користувач-власник через `users.find(...)` та його список позичених ID.
3. `Book.returnBook()` робить книгу доступною.
4. `User.returnBook()` видаляє ID книги зі списку користувача.
5. `persist()` зберігає новий стан.
6. `notify()` показує повідомлення, а функція `render()` у `app.ts` повторно викликає `renderLibrary()`, де кнопка змінюється на «Позичити».

Основні UI-фрагменти цієї логіки знаходяться у `src/ui/render.ts`, у функціях `addBorrowControls()` та `addReturnButton()`. Функція `renderLibrary()` запускає рендеринг списків. Методи моделей розташовані у `src/models/Book.ts` та `src/models/User.ts`, а збереження виконує `persist()` у `src/app.ts`.

## 13. Валідація форм

Валідація знаходиться у `src/utils/validators.ts`.

Для книги перевіряються:

- заповнені назва та автор;
- рік складається з чотирьох цифр;
- рік входить у діапазон від 1000 до 2100.

Для користувача перевіряються:

- числовий ID через регулярний вираз `/^\d+$/`;
- непорожнє ім'я;
- коректний email.

Крім TypeScript-валідації, HTML-поля мають атрибути `required`, `pattern`, `type="email"` та обмеження числового поля. Помилки не виводяться через `alert`: вони показуються у власному повідомленні або модальному вікні.

Регулярний вираз `^\d+$` означає: від початку до кінця рядка дозволені тільки одна або більше цифр.

## 14. Система сповіщень і ліміт позик

У застосунку не використовується `alert`.

Для коротких повідомлень використовується функція `notify()`, яка показує toast. Для важливих дій використовується компонент `Modal` у `src/ui/components/Modal.ts`.

Модальні повідомлення використовуються для:

- вибір користувача зі списку;
- підтвердження успішної позики;
- повідомлення про повернення;
- повідомлення про помилки валідації;
- повідомлення про перевищення ліміту.

Один користувач може одночасно позичити максимум три книги. Четверта спроба повертає `false` з `User.borrowBook()` і блокується з поясненням для користувача.

## 15. Збереження даних після перезавантаження

Під час запуску застосунок виконує відновлення стану з LocalStorage. Після таких операцій викликається збереження:

- додавання книги;
- додавання користувача;
- видалення книги;
- видалення користувача;
- позичання книги;
- повернення книги.

Тому після перезавантаження сторінки книги, користувачі та їхні позики відновлюються.

Дані зберігаються у браузері, а не у файлах проєкту. Щоб побачити їх у браузері, можна відкрити DevTools і переглянути `Application` -> `Local Storage` -> `http://localhost:9000`.

## 16. ESLint і Prettier

Конфігурація ESLint знаходиться у `.eslintrc.json`, а Prettier - у `.prettierrc`.

ESLint аналізує код і знаходить потенційні помилки: невикористані змінні, порушення TypeScript-правил та небажане використання `any`.

Prettier відповідає за єдиний стиль форматування: відступи, лапки, довжину рядків та переноси.

Команди:

```bash
npm run lint
npm run format
npm run format:check
npm run typecheck
```

ESLint відповідає за якість і правила коду, а Prettier - за його зовнішнє форматування.

## 17. Автоматичні тести Mocha і Chai

Тести знаходяться у:

- `tests/library.test.ts`;
- `tests/validation.test.ts`.

У тестах використано Mocha як test runner і Chai для перевірок через `expect`.

Перевіряються такі сценарії `Library`:

- додавання об'єкта;

- видалення об'єкта;
- перевищення ліміту позик користувача.

Для `Validation` перевіряються:

- обов'язкові поля книги;
- некоректний рік;
- числовий ID користувача;

Запуск тестів:


## 18. Husky pre-commit hook

Файл `.husky/pre-commit` запускається автоматично перед створенням Git-коміту.

Він виконує:

```bash

```

Якщо ESLint або тести завершуються з помилкою, коміт блокується. Це не дозволяє зберегти у репозиторій код, який не проходить базові перевірки.

Husky підключено через поле `prepare` у `package.json`:

```json

```

## 19. Пошук книг

Пошук реалізований у `src/app.ts` через обробники полів пошуку, а фільтрація виконується у `src/ui/render.ts` у функціях `renderBooks()` та `renderUsers()`.

Текст із поля пошуку переводиться у нижній регістр, після чого перевіряється через `includes()` у назві та авторі книги. Тому користувач може ввести як повну назву, так і окрему її частину.

Пошук не змінює дані у бібліотеці. Він тільки змінює набір об'єктів, який показується на поточній сторінці.

Також передбачено пошук користувачів за іменем або email.

## 20. Видалення книг і користувачів

Для видалення використовується метод `Library.remove()`.

У списку книг є кнопка видалення книги. У списку користувачів є кнопка видалення користувача.

Перед видаленням користувача його позичені книги повертаються у доступний стан. Це потрібно, щоб після видалення користувача в системі не залишилися книги, які назавжди вважаються позиченими.

Після видалення оновлюється DOM і новий стан записується у LocalStorage.

## 21. Пагінація

Пагінація реалізована у `src/ui/render.ts` функцією `renderPagination()`.

Розмір однієї сторінки - 5 записів. Пагінація працює для:

- списку книг;
- списку користувачів.

Якщо користувач виконує пошук, пагінація працює вже для відфільтрованого списку. Після видалення або зміни кількості записів поточна сторінка коригується, щоб не показувати порожню сторінку.

## 22. Окремий варіант на Vite

У проєкті підготовлено Vite-варіант:

- `vite.config.ts` містить конфігурацію Vite;
- `index.html` є HTML-точкою входу для Vite;
- `npm run start:vite` запускає Vite dev-сервер;
- `npm run build:vite` створює збірку у `dist-vite`.

Vite використовує той самий TypeScript-код застосунку, але має інший механізм dev-сервера та production-збірки. Його root - коренева директорія `app-library`, тому `src/app.ts` підключається безпосередньо з `index.html`.

У поточному стані Webpack-конфігурація також залишається у проєкті, тому цей пункт реалізовано як підготовлений паралельний Vite-варіант, а не як повністю відокремлена migration-гілка з видаленням Webpack-залежностей. Для повного виконання вимоги потрібно створити окрему Git-гілку, видалити непотрібні Webpack-файли та залежності в цій гілці й перевірити, що застосунок працює ідентично.

## 23. Деплой на GitHub Pages

У поточному `package.json` немає окремого скрипта `deploy`, залежності `gh-pages` або GitHub Actions workflow для автоматичної публікації.

Тому факт деплою на GitHub Pages не можна підтвердити лише файлами поточного проєкту. Для повного виконання пункту можна додати:

```bash
npm install --save-dev gh-pages
```

Після цього у `package.json` можна створити скрипти для публікації директорії production-збірки, наприклад `dist` або `dist-vite`.

Також потрібно врахувати `publicPath` для Webpack або `base` для Vite, якщо репозиторій відкривається не з кореневого домену, а з адреси виду `username.github.io/repository-name`.

## 24. Порівняння Webpack і Vite

Webpack і Vite виконують однакову основну задачу - готують TypeScript, стилі та HTML до запуску в браузері, але працюють по-різному.

### Webpack

Webpack будує граф залежностей і збирає застосунок у bundle. Для цього у проєкті окремо налаштовані entry, output, loaders, plugins та dev-server.

Переваги:

- дуже гнучка конфігурація;
- велика екосистема loaders і plugins;
- зручний контроль усіх етапів збірки;
- добре підходить для складних або старих проєктів.

Недоліки:

- конфігурація довша;
- потрібно вручну налаштовувати loaders для TypeScript і SCSS;
- старт dev-сервера може бути повільнішим на великих проєктах.

### Vite

Vite у режимі розробки швидко запускає сервер і віддає модулі за потребою. Браузер завантажує потрібні модулі без попереднього повного bundle. Для production Vite використовує оптимізовану збірку.

Переваги:

- коротша конфігурація;
- швидкий старт dev-сервера;
- швидкий HMR;
- зручна робота з TypeScript і сучасними frontend-проєктами.

Недоліки:

- для нестандартних сценаріїв також можуть знадобитися plugins;
- міграція складного Webpack-проєкту може вимагати зміни конфігурації;
- production-результати потрібно перевіряти окремим build-командою.

Для невеликого SPA цього проєкту Vite зручніший у щоденній розробці через коротшу конфігурацію та швидкий dev-сервер. Webpack краще демонструє ручне налаштування loaders, plugins і повного процесу збірки, що також є важливою навчальною частиною лабораторної роботи.

Для повністю експериментального порівняння потрібно окремо заміряти:

- час виконання `npm start` і `npm run start:vite` до готовності сервера;
- швидкість HMR після зміни TypeScript або SCSS;
- час виконання `npm run build` і `npm run build:vite`;
- розмір файлів у `dist` і `dist-vite`.

# Висновок

У роботі створено клієнтський застосунок управління бібліотекою на TypeScript. Дані предметної області представлені класами `Book` і `User`, а робота з колекціями узагальнена через `Library<T>`. Відповідальність розподілена між моделями, сервісами, валідацією та UI.

Користувач може додавати, шукати та видаляти книги й користувачів, позичати та повертати книги. Дані не втрачаються після перезавантаження сторінки, тому що зберігаються у LocalStorage. Помилки та результати операцій показуються через власні повідомлення і модальні вікна без використання `alert`.

Проєкт збирається Webpack, має підготовлений Vite-варіант, використовує Bootstrap, ESLint, Prettier, Husky та Mocha з Chai. Команда `npm test` підтверджує проходження 8 автоматичних тестів.

Для повного завершення всіх пунктів звіту потрібно додатково оформити окрему Vite migration-гілку, налаштувати деплой на GitHub Pages і додати фактичні заміри Webpack та Vite.
